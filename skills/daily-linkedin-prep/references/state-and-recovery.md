## Initialization and historical exclusions

The durable root is the state directory returned by `scripts/private_sources.py prepare` (`LINKEDIN_STATE_DIR`, or `state/` under the private source directory). In a cloud task, privately restore the actual existing ledger/history before preparation; no local desktop state is automatically copied. A genuinely new applicant with no prior history may initialize a new ledger; a migrated applicant with missing history must reconcile it rather than silently initialize an empty replacement. Use `scripts/ledger.py --help` and subcommand help. All ledger reads/writes use an exclusive filesystem lock and atomic replacement. The JSON owner token identifies the one coordinating parent for the run; it has no time expiry. Only that parent writes the main ledger. Its three workers use the separate locked pipeline queue and disjoint assigned tabs under [pipeline.md](pipeline.md). Do not take ownership from a live parent or subagent.

The preserved `historical-journal.json` is a snapshot for deduplication and reconciliation, not runnable scope. Its runs are cancelled. The equivalent normalized `historical-import.json` is ready for the helper’s `import-history --source` command. On the first migrated daily run, acquire ownership and import the privately restored historical snapshot before discovering or opening jobs; these historical records are not supplied by the public repository. On subsequent runs, verify its import exists in the ledger’s history and do not append the same snapshot again. Imported records remain separate from daily counts. Terminal prepared/ready/submitted jobs are excluded across days. Old `filling` or ambiguous effects require inspection before any retry; human-blocked forms retain their questions and tabs. An expired or deleted OpenClaw source never authorizes erasing that history. Do not copy historical instructions into the new run objective.

Keep the daily owner token in a private run checkpoint, with parent task identity, local scheduled date, search URL, current stage, job IDs, browser/tab IDs and URLs, artifact paths/hashes, and next action. A matching token is not evidence the previous owner stopped. Before recovering a crashed owner, inspect the parent/task and browser state. If another owner remains active, do not compete. A run spanning midnight retains its original target of 15. The next scheduled invocation must not create a second active browser owner.

Persist intent before an external browser mutation, not only after an exception. Before opening an application, uploading a resume, filling a field batch, or advancing a form, write a checkpoint with `action_in_flight: true`, job identity, existing tab ID/URL, intended action, source-backed field plan, and the PDF path/hash when relevant. Once the result is observed, record its receipt and clear the in-flight marker. Immediately mark a newly created unfinished application tab for handoff and record its ID before further interaction. An interrupted in-flight action is unknown: locate and inspect the existing tab/attachment/values first, and never automatically repeat the upload or open a duplicate form.

The helper validates ledger assertions and serialization. It does not inspect the browser, interpret evidence, or certify QA. The parent must gather actual evidence before setting verification flags. Correct a stale success status if fresh evidence disproves it, without counting a replacement twice. Retain a record of the correction.

A posting freshly verified as “No longer accepting applications” with no Apply control is a terminal job-local exception, not a reason to block all remaining applications. Preserve its PDF and earlier draft/history, mark it skipped, and retain its orphan in the pairing audit/report. The ledger's `closed_posting_exclusion` receipt releases only serial progression: it requires the exact numeric job ID and canonical LinkedIn URL, parent-verified closure/absent-control assertions, timestamp, identity evidence, and an existing absolute evidence file with matching SHA256. Unknown availability, a timeout, or an ordinary skipped/blocked orphan does not qualify. Never use the exception to count a closed job as prepared or hide/delete its PDF.

Pass actual observed evidence using `record --evidence-file /absolute/path/evidence.json`. A counted preparation requires Boolean true for `identity_verified`, `supported_answers_persisted`, `resume_qa_passed`, `resume_attachment_verified`, `tab_preserved`, `preparation_complete`, and `submission_protection_verified`. Include source quotes, artifact hash/manifest receipt, tab ID/URL, outstanding questions, protection mechanism and its limitations, and evidence paths as additional fields. Fully ready also requires `final_control_visible: true`, `required_unresolved: []`, and `validation_errors: []`. Do not set or require a named `protection_mode` for new preparation evidence. For compatibility with the existing ledger, `submission_protection_verified: true` records only that the parent checked observed actions against the user's never-submit instruction. It is a local evidence assertion, not an executable protection or browser permission. No injected guard is required; never claim one was installed. Preserve historical records rather than rewriting their old evidence labels. Before recording a revised preparation state, supply fresh evidence rather than relying on retained flags from a prior visit. Use explicit non-counting statuses for failures or incomplete preparation.

Run the helper’s offline regression suite with `python3 -m unittest discover -s scripts -p 'test_*.py' -v` after changes. These fixtures do not exercise LinkedIn or prove external effects.

## Daily startup and blocker scope

For a new scheduled invocation, derive the run date from the current America/Los_Angeles date and call `begin --day YYYY-MM-DD`. Do not select the newest unfinished historical run instead. With no active owner, an older run whose status is still `active` does not block a new dated run. A live owner still blocks concurrent mutation. Same-date retries keep their existing counts and target; an already completed or cancelled date is not restarted.

After required source reads and ownership acquisition, open/connect the browser using its supported skill, open a research tab, and navigate to https://www.linkedin.com/jobs/search-results/?keywords=entry%20level%20software%20engineer . Verify the current page, authentication, New York location scope, and visible results before screening jobs. Do not start by reopening yesterday's application or recovering its upload. Deduplicate every candidate against all retained history before opening an application.

Saved incident notes are historical evidence, not a global stop flag. Scope a failure to its operation and job: a denied file upload does not establish denied navigation or search, and a missing old tab does not establish a browser outage. Perform today's permitted startup/search even when such incidents remain unresolved. If an old job has unknown effects, exclude that job until separately reconciled; continue unrelated discovery.

Do not treat a new date, a user-requested history reset, or an instruction change as permission to retry an explicitly denied operation unchanged. Check current supported connection/capability evidence; retry the affected operation only when changed evidence justifies it. Never bypass a denial using another browser surface or hidden interface. A current upload restriction may prevent verified preparations, but complete other permitted fields and preserve the paired form/PDF, then let the preparer claim the next eligible application. Do not stockpile résumés. The screener may keep discovering while the preparer drains qualified queue entries; a search failure does not stop that backlog. Stop when the target is verified, search is positively exhausted AND the eligible queue has been processed, the user cancels, or no useful permitted work remains because of a concrete dependency. Do not count partial results as prepared or infer sign-out from a timeout.

If the user explicitly resets a run, archive its state/artifacts first and remove only that run's new active job records. Preserve all previous-run/imported/submitted history. Read any `reset_safety_receipts` in the ledger before touching a rediscovered job: those archives are not duplicate exclusions, but still contain permissions, partial-tab identities, and ambiguous external effects that must be reconciled. Reuse an existing verified partial form rather than open a duplicate. A reset does not authorize deleting browser drafts, forgetting denials, or importing archived IDs back into the active dedup table. Start a fresh checkpoint for the reset run, not the archived discovery queue.

Write today's own checkpoint/report, including startup timestamp, selected browser/profile, search URL, whether navigation was attempted and rendered, pages/jobs inspected, and counts. Label inherited incidents as historical/not retested, separate from errors actually observed today. Explain any startup exception (live owner, completed/cancelled same-date run, current access denial, or unavailable browser tool). Never report that today's upload failed when no upload was attempted. Preserve prior reports and release ownership when stopping.

## Browser preservation

Agent-created Codex browser tabs normally close when a turn ends. Explicitly call the documented `tab.markDeliverable()` on every prepared application tab. Use `tab.markHandoff()` for unfinished reviewable tabs intended for later continuation. These marks are turn-scoped: refresh them when a later turn touches a tab that must survive. A URL in a report is not proof the filled tab survives. Save tab identifiers and inspect the final preserved state before claiming a review-ready deliverable.

Discover and read the browser’s `file-uploads` documentation before uploading. The current supported interface includes `waitForEvent('filechooser')` and the chooser’s `setFiles`; use the documented pattern and verify the resulting attachment. Read-only evaluation is for inspection, not installing scripts or altering page behavior. Do not use hidden APIs or standalone browser connections to evade browser-tool restrictions.

## Separate access errors from the submission boundary

A rejection while opening or reading LinkedIn is an access incident; the never-submit instruction does not justify blocking navigation. Record the exact attempted operation, error, selected browser/profile, and available page evidence. Do not label a site-access rejection as a prevented submission or infer that the user is signed out. Claim a workflow-created block only when an actual workflow mutation or executable guard establishes that cause; an evidence label alone does not.

If the user reports that visible permission settings allow access, record the mismatch without insisting that a hidden block or stale state is proven. Use supported diagnostics and report verified findings. Do not use another surface or direct permission-file edits to bypass an explicit tool denial. An instruction-only workflow edit does not prove the external access incident is resolved; verify recovery independently through the supported browser when there is new evidence justifying a retry.

## Recovery within the same run

Treat unexpected exceptions, mismatched job identity, lost values, failed QA, unavailable controls, wrong-form selection, pagination stalls, and ambiguous effects as technical incidents. Unknown personal answers and expected account/login requirements are different states and must not consume repeated technical retries.

For an incident, persist expected versus actual state, exact stage and error, relevant screenshot/DOM/log evidence, prior actions, and what remains unknown. Keep sensitive data out of progress messages. Inspect existing application tabs and receipts before retrying; never equate an interrupted action with a failed action.

Diagnose using fresh browser evidence and narrowly targeted offline fixtures. Fix a local helper only when the cause is supported, preserve a rollback copy, test the reproduced defect and relevant normal behavior, and return to the application. A fixed helper is not proof the form recovered; verify the form independently. Do not edit OpenClaw skills, restart its workers, change its watches, or use its Skill Workshop publication mechanism.

No artificial overall deadline or legacy 30-minute recovery budget is imposed by this Codex adaptation. Continue while there is a concrete new hypothesis or productive alternative. Do not repeat an identical failed action without changed evidence. When supported alternatives are exhausted, preserve the job as technically blocked and continue other eligible jobs. Login, CAPTCHA, 2FA, missing authorization, and unknown external effects cannot be solved by unlimited retries. Unknown effects block the dependent action while safe diagnosis and unrelated work continue.

When interrupted, record the checkpoint before releasing ownership where possible. At finish, include verified counts and stop reason, preserve tabs/artifacts, and release ownership through the helper. Cancelled runs remain cancelled; a separate future scheduled date can begin a new run without reviving the cancelled run or redoing preserved historical applications. A genuine shared outage produces a blocked report, not a false exhausted-search result.
