## Roles and ownership

### Current browser transport restriction (verified September 29)

The live multi-session pilot failed final handoff: worker-created application tabs changed IDs and timed out when reclaimed by the parent, while parent-created tabs remained readable. Therefore **use one parent browser session as the sole browser executor by default**. The three workers still own their logical responsibilities and queue/files, but send bounded, evidence-grounded browser work requests to the parent. The parent alone opens research/application/tracker tabs, performs all reads and writes under the exclusive lease, and returns compact evidence to the requesting worker. The preparer still owns one job end-to-end and produces its résumé; the recorder still drafts and verifies done-only tracking through parent-returned evidence. Never run worker browser sessions concurrently or hand off newly created live forms across sessions merely because tab URLs match.

This restriction overrides the direct worker browser/tab-ownership instructions below until a future explicit, non-application test proves cross-session handoff preserves readable state. Keep all existing failed handoffs as reconciliation-needed, retain PDFs/history/Notion rows, and never recreate drafts blindly. A changed tab ID plus unreadable form cannot pass the final pairing gate. Workers must stop their whole browser-request batch if the parent cannot acquire the lease; setup or read-only calls are not exempt. Application completion and Notion logging remain independent evidence gates, and a final audit may revoke an earlier done receipt.

| Role | Owns | Must not do |
| --- | --- | --- |
| `linkedin-screener` | Its research tab, current job discovery, qualification evidence, queue additions, `screening-progress.json` | Open/fill application dialogs, make PDFs, edit main ledger or Notion |
| `application-preparer` | One claimed application at a time, distinct application tabs, its own read-only history-lookup tab, supported answers, résumé package and QA, upload, final evidence | Submit, prepare several jobs at once, change the screener/recorder tabs or write Notion rows, call a PDF “done” |
| `notion-recorder` | Its tracker tab, `notion-tracking.json`, Notion claims for `done` entries, verified row receipts | Read queued/blocked job details for logging, change application forms, make PDFs, count drafts as submitted |
| Parent | Main ledger owner token, role dispatch, final evidence checks, queue/ledger reconciliation, user replies, run stop and report | Mutate a worker-owned tab without an explicit handback |

At startup save `workers.json` with run ID, target, parent identity, each worker identity, assigned tab IDs, claimed job ID, and last handoff. The parent alone writes this ownership map. Never share the main ledger owner token with workers. Every worker reads SKILL.md and applicable linked instructions itself before acting. Give the screener and preparer the preserved sources and user corrections; give the recorder only completed-job receipts needed for tracking, not private candidate answers.

Distinct tabs are required. A job URL is not enough to establish tab ownership. Only the preparer manipulates application forms. The screener can navigate its research tab and the recorder its Notion tab. Prefer tab-scoped supported controls; avoid global focus, keyboard or file-chooser collisions. If the runtime shares focus/choosers or denies cross-agent tab access, the parent schedules short browser turns with explicit handoffs, while qualification, résumé work, and queue work continue independently. Never use a hidden API or different browser to bypass a denied action. Each browser worker reads the installed browser skill and current runtime documentation, uses a role-specific binding, and preserves its deliverable tabs before yielding.

The preparer may use a separate read-only Notion history-lookup tab for mandatory pre-application duplicate checks, under its application browser lease. It must not create/update database rows or touch the recorder's tab. This prevents history checks from waiting on the done-only recorder; the recorder still consumes only done queue entries. Give lookup findings to the parent when identity is ambiguous rather than writing or downgrading a historical row.

Use the helper's exclusive `claim-browser` / `release-browser` lease for each short browser batch, including discovery navigation, Notion reads/writes and application clicks/uploads. Application/Notion leases require that role's current job claim token. The discovery lease uses the screener identity; during initialization/reconciliation the parent may use a discovery lease explicitly labeled as parent maintenance. Do not hold a browser lease while drafting a PDF, waiting for user input, or waiting for the parent. Release it after saving the batch receipt. A failed batch retains an uncertain action checkpoint; release normally if the worker can do so, otherwise parent-only `recover-browser` requires verified stopped ownership and state inspection. File-chooser open plus setFiles and its immediate receipt are one indivisible browser batch. No worker touches a browser while another owns this lease. This deliberately serializes UI operations while allowing independent reasoning, document production, and queue work in parallel.

The atomic lease, not a chat handoff message, is the source of truth. A worker ready for UI work may claim a free lease directly without another parent permission round trip. On a busy lease, do useful offline work or await its release event; do not busy-poll. Notify waiting roles when releasing, but do not treat old suggested turn order as a permanent reservation that leaves a free browser idle. Parent arbitrates only actual contention or a stalled owner.

## Shared queue and evidence

Use `RUN/pipeline.json` through `scripts/pipeline_queue.py`, never ad-hoc read-modify-write. The helper locks and atomically replaces state, validates claim tokens and completion against the main ledger, and preserves events. Read [queue-commands.md](queue-commands.md) and its `--help` before operating the queue. The main ledger remains authoritative for daily count and historical duplicate prevention; the queue schedules work, not truth. Save claim and browser-lease tokens in private role checkpoints; ordinary status output may redact them. Do not invent a replacement token on retry.

One entry per LinkedIn job ID, with company, exact title, location, job URL, observed application URL, ATS job ID when available, qualification score and requirement evidence, salary evidence, discovery/check timestamps, duplicate-check sources/result, application status, claim owner/token, review-tab ID/URL, resume path/hash, unresolved questions, blockers, and separate Notion status/row URL. Store long job descriptions and source mappings as referenced per-job evidence files rather than copying them into every message. For Easy Apply, the LinkedIn job URL is a valid application link. An external destination not yet observed is unknown, not a guessed URL; retain the LinkedIn entry link until the preparer resolves it.

On observing an external destination, the preparer calls `bind` with its claim token, observed URL and provider-qualified ATS identity before filling personal fields. Check that identity against historical ledger/submission sources too; queue dedup only covers this queue. A returned duplicate conflict stops that application: preserve evidence, ask the parent to reconcile and mark the duplicate `skipped` without clearing history. Never retry a conflict as though it were a transient upload failure.

Application lifecycle: `ready_for_application → in_progress → done`. Exceptions are `blocked`, `needs_user_input`, `skipped`, or `reconciliation_needed`, never disguised as `done`. Keep Notion lifecycle separate: pending, claimed, `notion_logged`, or tracking blocked. Notion failure does not undo a valid prepared application or stop other applications.

`done` requires a same-run main-ledger `prepared_for_review` or `ready_for_review` record, all preparation gates, an existing QA PDF, verified attachment and supported fields, a distinct preserved application tab, and no technical incompleteness. Unknown personal answers may remain only under the existing `prepared_for_review` definition. `fully_ready` is a subset. No résumé-only, blank-form, failed-upload, listing-tab, or made-up verification status passes.

## Screener loop

1. Start fresh discovery on each new local scheduled date after parent ownership checks. Resume the same date's research checkpoint on retries. Verify LinkedIn authentication and New York, NY filters. Record actual startup and pagination evidence.
2. Inspect current descriptions, apply every hard filter and score required qualifications strictly above 60 against supported facts. Record all inspected IDs, exclusions, unknown eligibility and explanations; count card observations separately from full descriptions and unique jobs.
3. Check main ledger, historical/imported submissions, reset safety receipts, and available previously verified tracker history. Exact ID and normalized ATS URL matter; employer/title alone does not prove a duplicate. If a final external identity or live tracker check remains unresolved, state that prominently for the preparer's mandatory recheck. Known prior submitted/prepared/ambiguous applications never enter the ready queue.
4. Add every verified eligible, clear candidate to `ready_for_application`, with evidence and observed links. Never record a queued candidate as active `qualified` in the main ledger, which would block the preparer. Notify the parent/preparer when useful work becomes available; do not wait to collect a batch of 15.
5. Continue qualifying while the preparer works. Stop discovery at the verified target, user stop, positive search exhaustion, or a current discovery blocker. A temporary empty queue is not exhaustion. Do not stop because a page/time/card budget elapsed. If the search is exhausted, save the final-results evidence and let the preparer drain the queue. Queue leftovers after reaching the target are retained, not silently treated as next day's prepared applications.

## Preparer loop

1. Reconcile any inherited in-flight action and existing tab first. Atomically claim the next ready entry (one application claim globally). Recheck current job identity, status, ATS identity and duplicate history before entering personal information; ask the parent to record the claimed job as `qualified` in the main ledger.
2. Open or reuse that job's actual application, preserve the tab, fill all accessible supported fields, and checkpoint mutation intent/results. Unknown optional answers stay blank; ask concise asynchronous questions for material required unknowns, continue after a short opportunity to answer, and list unresolved questions. Never invent defaults for eligibility, consent, salary, dates, or sensitive answers. User replies are routed by the parent to the relevant job and saved with provenance.
3. Send the filled-form evidence to the parent for ledger `check-next --for-resume`. After a passing result, create and QA only this job's résumé using resume-quality.md. Compile, extract text, render/inspect each page, and hash the exact file. Then upload using the currently observed **résumé field**, not an autofill/cover-letter control with similar text. Verify both accepted attachment placement and supported answers after upload.
4. Advance only proven non-final steps. Leave the final submit control untouched. Mark the filled tab for preservation. Send a compact receipt with evidence paths, PDF/hash, tab, verified fields/attachment, final-control evidence, remaining questions and application claim token to the parent. Parent verifies consistency and fresh browser evidence without competing for the tab, records the main-ledger status, and calls the queue helper's parent-only completion command. Only that acknowledgment changes the application to `done`. The preparer never receives the main ledger owner token.
5. For technical blockage, preserve the paired tab/artifact and exact cause, ask parent to record a non-counting status, release the application claim through the helper and move to the next entry. Do not retry a denied operation unchanged. Resolve orphan/lost-tab mismatches before creating another PDF. Empty queue while the screener is active means wait for a queue event or parent follow-up, not finish the run.

## Notion loop: done entries only

Atomically claim a `done` entry with pending tracking. Recheck its main-ledger prepared status before writing; request parent correction if stale. Search live Notion by job ID and normalized URL; preserve submitted/interview/rejected rows and human notes. Write intent before each external mutation, save the row URL immediately after creation, fill exact properties and preparation note under SKILL.md, leave Application Date blank, then reopen and verify. Record the row URL and verified receipt in both `notion-tracking.json` and the queue's separate Notion result. Never erase application status `done` merely because it has been logged.

Do not create rows for blocked, queued, screening-only or incomplete jobs. Preserve pre-existing blocked rows and update only when that exact job becomes done. This is the user's September 29 change to the previous blocked-job tracking rule. If a write times out, its outcome is uncertain: inspect for an existing row before retrying. Keep pending receipt and continue another done entry where safe. Only this worker writes the tracking file and tracker tab. The parent consumes its receipts, not duplicate writes.

## Parent orchestration and recovery

Dispatch the three roles with this reference, stable run/queue paths, target, tab assignments, and current checkpoints. Initial assignments may be bounded setup work until dependencies are ready. Send evidence-path messages rather than entire browser snapshots. Use event-driven follow-ups when a queue changes; no busy polling or independent background promises after a turn ends. Keep the user informed of real stage counts and new blockers, without narrating every field click.

Migrate an active run without resetting history: retain target and prepared count; audit the existing prepared tabs and import them as done only through ledger-backed verification; copy existing verified Notion receipts without duplicating rows; reconcile the in-flight application before handing it to the preparer. Current-run screening-only eligible items can enter the queue with fresh checks. Old unfinished applications are not automatically today's scope. Preserve all older records and denial history.

Claims never expire merely because time passes. After an interruption, verify the worker is stopped and inspect the affected browser state before explicit recovery; do not blindly reset claims or replay uploads/writes. If the helper lacks a needed transition, checkpoint and use parent-directed reconciliation rather than edit queue JSON. Changes to files do not prove browser recovery.

If fresh browser evidence disproves a `done` application's preparation, the parent first corrects the main ledger and then uses parent-only `invalidate` with the exact reason to move the queue entry to `reconciliation_needed` and suspend tracking. Preserve receipts and existing Notion rows. Reconcile any active claim/lease before invalidation. This prevents a stale done entry from repeatedly blocking valid later Notion work; only new evidence and an explicit parent retry can requeue it.

Stop new claims at the target, then drain done-entry Notion tracking, refresh every prepared tab's preservation mark, perform live pairing checks and `ledger.py audit-pairs`, and report: unique screened, fully assessed, qualified/queued, prepared out of target, fully ready, prepared with questions, blocked/skipped, Notion logged/pending, and stop reason. Search exhaustion is terminal only after the ready/in-progress queue is drained. On user cancellation or a real shared blocker, stop workers, preserve checkpoints and tabs, report partial results and release parent ownership. Do not change schedules except the explicitly requested workflow prompt update.
